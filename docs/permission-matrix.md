# Permission matrix

Status: draft, to be validated in the tenant

Verified against official documentation on 2026-11-11

## 1. Purpose and blocking rule

This document fulfils the "Mandatory matrix" in section 8 of the specification. It has one row per operation. Each row states the API and version, mode, identity, exact permission, grant on the resource, administrative role, licence, documentary evidence and negative test.

Rule of the specification: any incomplete row blocks the real implementation of that operation. A row is INCOMPLETE when at least one of its fields is not verified in official documentation. The missing fields are referenced by codes L01 to L18, listed in section 6 together with the way to unblock them.

Result of this version: no row is complete. Every row is INCOMPLETE. For that reason, no real adapter for Entra, Graph or Exchange can be implemented from this document. Phase B (the local slice in .NET 8) uses simulated adapters, marked as simulation, and remains the limit of what exists. Phases C, D and E have not been executed and the Bicep has never been applied.

The "Evidence" column cites Microsoft Learn pages. All were verified on 2026-11-11. URL prefix when abbreviated: `https://learn.microsoft.com/en-us/`.

Legend:

- Verified: text read on the page.
- Inference: conclusion drawn from verified texts. It is not written in the documentation.
- NOT VERIFIED: the documentation read does not state it, or the page was read only as an excerpt.
- Identities: "agent" (the agent runtime, which never receives the data credential), "executor" (separate execution identity per agent, `ExecutorObjectId`, holds the data credential), "control identity" (privileged control service, never used by the agent runtime) and "operator" (person with a role, through the control API or the admin centre).

## 2. Contradictions in focus

### Contradiction A. Least privilege for reading with Selected

Verified. The four read pages (`drive-list`, `driveitem-list-children`, `driveitem-get`, `driveitem-get-content`, all v1.0) do not list any `*.Selected` scope in the application permissions table. The least-privileged permission they indicate is `Files.Read.All`. That permission has tenant-wide scope and defeats the purpose of the project.

Verified. The Selected overview states the opposite: the Selected scopes give access to these resources through the paths `/drives/{driveid}/items/{itemid}` and `/sites/{siteid}/lists/{listid}/items/{itemid}`, and the `read` role is "Read the metadata and contents of the resource". Source: `https://learn.microsoft.com/en-us/graph/permissions-selected-overview`.

Inference. According to the documented model, the least-privileged permission for the MVP is `Sites.Selected` (or `Lists.SelectedOperations.Selected` for a single library), in application mode, with the `read` role assigned on the resource.

Design decision while there is no tenant test: do not use `Files.Read.All`, `Sites.Read.All` or `Sites.ReadWrite.All` to work around the difficulty (specification, section 8). If an endpoint rejects the Selected token, the operation stays blocked and the gap is recorded. It is not hidden with simulation.

### Contradiction B. Permission to grant on a list and an item

Verified. To assign permissions on a list, the Selected overview requires `Sites.FullControl.All`, `Sites.Selected` with the FullControl role, or `Sites.Selected` with the Owner role. For an item and a file it adds `Lists.SelectedOperations.Selected` with FullControl or Owner. Source: `https://learn.microsoft.com/en-us/graph/permissions-selected-overview`.

Verified. The API reference (`list-post-permissions` and `listitem-post-permissions`, v1.0 and beta) gives `Sites.ReadWrite.All` as the least privilege, with `Sites.FullControl.All` and `Sites.Manage.All` as higher ones, and does not list any `*.Selected` scope. Sources: `https://learn.microsoft.com/en-us/graph/api/list-post-permissions?view=graph-rest-1.0` and `https://learn.microsoft.com/en-us/graph/api/listitem-post-permissions?view=graph-rest-1.0`.

The two pages cannot both be true. Only a test in the tenant decides. Design decision until then: assume the stronger requirement (the overview). Risk note: `Sites.ReadWrite.All` would be a tenant-wide write permission, which is unacceptable for a granting identity.

### Contradiction C. Asymmetry between creating and removing a grant on the site

Verified. Creating a permission on the site accepts delegated and application mode (`Sites.FullControl.All`). Removing a permission on the site accepts application mode only ("Not supported." in delegated). Sources: `https://learn.microsoft.com/en-us/graph/api/site-post-permissions?view=graph-rest-1.0` and `https://learn.microsoft.com/graph/api/site-delete-permission?view=graph-rest-1.0`.

Verified consequence: revoking the grant on the site requires an application identity with `Sites.FullControl.All`. The documented alternative is to revoke consent in Entra, which cuts access to any list on which the scope was granted.

### Other divergences that affect the matrix

- Blueprint versus blueprint principal (C6 of the research): the "Agent blueprints" list is described as blueprints on one page and as blueprint principals on another. Affects I02.
- Meaning of `accountEnabled` (C10): the Graph reference says "no users are able to sign in to this app", while the administration pages say "block its access and token issuance". Affects I01 and I02.
- Validity of the pre-authenticated download URL: "might expire within minutes" on one page and "1 hour" on another. Use 1 hour as the worst case. Affects M04.
- Graph version of `isDisabled` on application: disable in beta, re-enable in v1.0, on the same page (C7). Affects S01 (see the note on `isDisabled` in section 5).

Notes on the data operations:

- Paging (M02): the page states 200 items by default and `@odata.nextLink` as an absolute URL. Inference: the executor validates the URL against the allowlist before following it.
- M03 and M04: `GET driveItem` returns `@microsoft.graph.downloadUrl`, which downloads without a token. Inference: getting metadata also hands over the ability to download, so the executor must remove the property. The executor follows the `302` itself, hands over only bytes and never logs the URL.
- M04: removing permissions "might not immediately invalidate the URL". There is a residual window for each URL already issued. The window is measured in the negative test, not assumed.
- Throttling: SharePoint Online returns `429` or `503` with `Retry-After`. The executor honours `Retry-After`. Do not depend on the `RateLimit` headers (the same page recommends them and states that SharePoint Online does not support them). Source: `https://learn.microsoft.com/en-us/sharepoint/dev/general-development/how-to-avoid-getting-throttled-or-blocked-in-sharepoint-online`.
- Composite requests: `POST /v1.0/$batch` and `POST /beta/$batch` accept up to 20 inner requests and the outer `200` status does not reflect the inner ones. Source: `https://learn.microsoft.com/en-us/graph/json-batching`. Inference: deny `$batch` by default. It has no row of its own because it is not a catalogue operation.
